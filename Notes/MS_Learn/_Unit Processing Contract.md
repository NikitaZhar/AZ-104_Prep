# Unit Processing — Contract

Инструкция-задание для исполнителя (Claude): **обработка юнита/модуля после того, как я вставил
сырой текст**. Цель — привести заметку к единому виду: унифицировать Properties, построить
навигационные связи, расставить ссылки на глоссарий (сверив термины и добавив новые из инбокса),
а при необходимости нормализовать заметки старого формата.

Смежные документы: имена и нумерация — [[_Numbering Plan]]; сборка тестов — [[_Quiz Builder Contract]]
(запускается **отдельно и позже**, этот контракт тесты не трогает).

---

## 0. Рабочий цикл

Два сценария, одна инструкция (§1–§6).

### 0.A Новый юнит (вставлен сырой текст)
1. Определить место в структуре по [[_Numbering Plan]]: трек → модуль → юнит; задать имя файла.
2. Проставить **Properties** (§1) и **связи** (§3).
3. Прогнать **глоссарий** (§4): сверить термины в тексте, обработать инбокс `Add to Glossary`,
   расставить ссылки на вхождения.
4. **Верификация** (§6). О том, что проверено программно, а что содержательно — говорить честно (§7).

### 0.B Нормализация legacy-заметки
1. Распознать признаки старого формата (§5).
2. Привести Properties, имена и связи к канону (§1–§3), не меняя содержательный текст.
3. Глоссарий (§4) и верификация (§6) — как в 0.A.

## 1. Канонические Properties (frontmatter)

Единая схема для всех заметок-юнитов. Поля и порядок:

| Поле | Обяз. | Значение |
|---|---|---|
| `created` | да | Дата создания `YYYY-MM-DD` |
| `type` | да | Принадлежность: `LP` (входит в официальный learning path AZ-104, треки 2–6) \| `Additional` (prereq/extra, треки 0–1). **Роль** (module/unit/lab) в `type` не кодируется. |
| `status` | да | Готовность: `draft` (создано) → `unit-processed` (Properties+связи+глоссарий) → `tests-built` (собраны Quiz/Practice/Lab) → `complete` (после всех проверок). |
| `part` | да | Название learning path (например, `Manage cloud resources by using Windows PowerShell`) |
| `module` | да\* | Обратная ссылка на индекс-заметку модуля: `"[[<N.N> ModuleName>]]"` (\*кроме самой заметки-модуля и standalone-заметок в корне трека) |
| `mslearn` | если есть | Прямой URL юнита на Microsoft Learn |
| `tags` | да | Список kebab-case тегов по содержанию |
| `prev` | кроме первого | `"[[<предыдущий юнит>]]"` |
| `next` | кроме последнего | `"[[<следующий юнит>]]"` |

Порядок полей: `created, type, status, part, module, mslearn, tags, prev, next`.

Правила:
- Значения-ссылки в кавычках (`"[[...]]"`), т.к. начинаются с `[`.
- **Роль заметки определяется нумерацией и именем файла, не полем `type`:** индекс-модуля — файл, чьё имя совпадает с именем папки (`<N.N> Name/<N.N> Name.md`); юнит — файл с более глубоким номером (`<N.N.N>`); lab/quiz/practice — суффикс ` — Lab` / ` — Quiz` / ` — Practice`.
- Индекс-модуля вместо `prev`/`next` уровня юнита несёт `next` на следующий модуль и список юнитов в теле.
- `status` — жизненный цикл заметки/модуля. **Потолок этого контракта — `unit-processed`** (и для юнита, и для модуля): обработка юнита выше него статус не поднимает. `tests-built` выставляет [[_Quiz Builder Contract]] после сборки тестов; `complete` ставится только вручную после всех проверок.
- Отдельного флага «в LP» в тегах не нужно — это поле `type` (`LP`/`Additional`).

## 2. Именование и размещение

- Имена и вложенность — строго по [[_Numbering Plan]] (`трек.модуль.юнит`, напр. `0.1.1.2 Review Azure PowerShell`).
- Модуль = папка `<N.N.N> ModuleName/`, внутри: индекс `<N.N.N> ModuleName.md` (имя = имени папки),
  юниты `<...>.md`, при наличии — html-исходник. Файлы Quiz/Practice/Lab лежат в той же папке, но их
  создаёт и именует [[_Quiz Builder Contract]] — этот контракт их не касается.
- Индекс-заметка модуля в теле содержит: ссылку на MS Learn, список юнитов `[[...]]` и стаб `## Summary`.
- **Блок `## Тесты` в индексе — не в зоне этого контракта.** Его создаёт и ведёт [[_Quiz Builder Contract]]
  (запускается отдельно и позже). Обработка юнита не добавляет, не заполняет и не трогает этот блок.
- **Скачанная страница MS Learn** (`<N.N.N> ModuleName.html`) — это исходник; в индексе она помечается
  как «сохранённая страница MS Learn / исходник».

---

## 3. Связи (навигация)

- **Сквозная цепочка** `prev`/`next` по юнитам модуля: первый юнит — без `prev`, последний — `next`
  на **первый юнит следующего модуля** (а если у него ещё нет юнитов — на индекс следующего модуля).
- **Обратная ссылка** `module` у каждого юнита — на индекс своего модуля.
- **Индекс модуля** перечисляет все юниты по порядку и имеет `next` на следующий модуль.
- Служебные knowledge-check/assessment юниты MS Learn в список не включаются (как в prereq-модулях) —
  нумерация юнитов идёт подряд без них.

## 4. Глоссарий: термины и ссылки

Единый файл [[Glossary]] (`### Термин` под секцией `## <модуль>`), запись = абзац-**определение** +
абзац-**описание**. Инбокс новых терминов — [[Add to Glossary]].

### 4.1 Источник терминов
Термины для проверки/линковки = все записи [[Glossary]] **плюс** термины из инбокса `Add to Glossary`.

### 4.2 Обработка инбокса
**Определения берутся ТОЛЬКО из учебного текста MS Learn** обрабатываемого модуля — не из общей базы,
не из знаний исполнителя. Своё определение придумывать запрещено.

Для каждого термина инбокса:
- **Уже есть в глоссарии** → запись не дублировать; только проставить ссылки на вхождения (и, по желанию,
  добавить в запись ссылку на новый юнит).
- **Определён в тексте текущего модуля** → добавить запись: определение (дословно/близко к тексту модуля) +
  описание (контекст, правила, примеры оттуда же) + ссылки на юниты, где термин встречается.
- **Встречается, но в модуле не раскрыт** (prerequisite и т.п.) → создать запись-**заглушку без определения**
  и пометить: `_(Определение — из MS Learn; в этом модуле термин только упомянут, не раскрыт. Заполнить, когда
  появится модуль, где он определяется.)_` Тело определения оставить пустым — не подставлять общую базу.
- После обработки — **очистить инбокс**, оставив закомментированный лог обработанного (`<!-- ... -->`).

> Глоссарий ведётся как отдельный workstream: любое определение должно иметь источник в MS Learn. Термин без
> такого источника остаётся заглушкой до модуля, где он раскрывается.

### 4.3 Правила линковки вхождений
- **Все вхождения** термина (текущая политика), формат `[[Glossary#Термин|видимый текст]]`.
- **Longest-first**: сначала длинные фразы (`Az PowerShell module`), потом короткие (`Az module`), чтобы
  не рвать длинные термины.
- **Границы слова**: не линковать внутри идентификаторов (`New-AzureRMVm` не трогать) — использовать
  негативные окружения `(?<![\w-])` … `(?![\w-])`.
- **Обходить (protected spans)**: frontmatter; fenced-код ` ``` … ``` `; инлайн-код `` `...` ``;
  уже существующие `[[...]]`; markdown-ссылки `[текст](url)`; голые URL; строки-заголовки (`#`, `##`…).
  → Термины внутри кода не линкуются (там команды/cmdlet'ы). Если понятие оформлено как код, но это
  термин — сначала снять backticks, затем линковать.
- **Идемпотентность**: повторный прогон безопасен — существующие `[[...]]` пропускаются, дублей нет.

### 4.4 Defined vs prerequisite
Линкуются **оба** типа терминов, если запись в глоссарии есть. Провенанс различается только пометкой
в самой записи (§4.2), на факт линковки не влияет.

### 4.5 Область прогона
По умолчанию — обрабатываемый юнит/модуль. При запросе «обновить всё» — весь материал, **кроме**
`Glossary.md`, `Add to Glossary.md`, `_*` (meta-документы) и папки `Review/`. Savill трогать только по
явному указанию.

## 5. Legacy-нормализация (старый формат)

Признаки и преобразования (содержательный текст не меняется):
- **Старая нумерация** имён/папок (`01`, `08.03`, `00.01`) → привести к схеме [[_Numbering Plan]],
  обновив все `[[ссылки]]`.
- **Старые Properties**: поля `chapter: N` и `section:` → убрать (номер/группировка уже в имени и нумерации) и добавить `module` backlink;
  поле `lp:` → убрать; старые значения `type` (`unit`/`module`/`lab`/`extra`) → заменить на `LP`/`Additional` (по треку: 0–1 → `Additional`, 2–6 → `LP`); проставить недостающие `type`, `status`, `mslearn`.
- **Термины в backticks**, которые на деле понятия глоссария (не команды) → снять backticks, затем
  линковать (§4.3).
- **Отсутствуют `prev`/`next`** → достроить цепочку (§3).
- **Битые/старые `[[ссылки]]`** после переименований → обновить под новые имена.

## 6. Верификация (после обработки)

- **Frontmatter**: все обязательные поля §1 присутствуют; значения-ссылки в кавычках.
- **Связи**: `prev`/`next` согласованы (next.prev указывает назад), `module` резолвится, юнит есть в списке индекса.
- **Глоссарий**: каждая `[[Glossary#H]]` указывает на существующий заголовок; нет висячих ссылок и
  нет вложенных/двойных скобок (`[[[`, `]]]`, `[[…[[`).
- **Инбокс** очищен, лог обработанного оставлен.
- Прогнать общий link-audit вейла (нет висячих `[[...]]`, нет дублей имён заметок).
- Аудит ссылок **исключает мета-документы** (`_*.md`: контракты, план) — они содержат примеры
  синтаксиса ссылок (`[[Glossary#Термин|текст]]`) и дают ложные срабатывания.

---

## 7. Честные границы

Механически проверяемо: наличие полей, согласованность `prev`/`next`, резолвинг ссылок глоссария,
отсутствие висячих/вложенных ссылок, идемпотентность линковки.

Требует содержательной проверки (и честно проговаривается): корректность и провенанс определений
(из модуля vs общая база), правильность отнесения термина к модулю/юниту, уместность линковки в
конкретном контексте. Если не уверен — говорить прямо, а не выдавать за проверенное.

## 8. Связь с другими контрактами

- **[[_Numbering Plan]]** — источник имён и вложенности (§2, §5).
- **[[_Quiz Builder Contract]]** — сборка Quiz/Practice/Lab **и** ведение блока `## Тесты` в индексе модуля;
  запускается **отдельно после** обработки юнита этим контрактом и **только по явному запросу** (не
  автоматически). Обработка юнита тестовые файлы и блок «Тесты» не создаёт и не трогает.
